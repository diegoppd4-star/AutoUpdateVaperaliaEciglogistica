# DB Refresh Model Notes

## Context

This note captures the current discussion around how Pipeline 6 should update an already populated DB when a later scrape changes the product set or matching state.

The current loader is application-ID driven. It inserts/upserts `referencias`, `referencia_distribuidora_links`, and `distribuidoras` with IDs generated by the pipeline, not by the DB.

## Current Behavior Observed

- `referencias.id` is supplied by `load_master_to_postgres.py`.
- The ID is generated as a bigint from `sha256("referencia:" + _source_key)`.
- `_source_key` includes the current master bucket:
  - `matched_both:<record.id>`
  - `only_eciglogistica:<record.id>`
  - `only_vaperalia:<record.id>`
- Because of that, a product can get a different `referencias.id` when it moves from `only_*` to `matched_both`.
- The loader uses `insert ... on conflict (id) do update`.
- The loader does not delete missing rows.
- The loader does not deactivate missing rows.
- The loader currently writes `referencia_distribuidora_links.activo = true` for every link in the current payload.

## Reclassification Problem

Example:

1. Run 1: an Eciglogistica product has no Vaperalia match.
   - It is written to `master_only_eciglogistica.json`.
   - The DB gets one `referencias` row and one Eciglogistica link.

2. Run 2: the matching pipeline finds a Vaperalia match for that same Eciglogistica product.
   - It is written to `master_matched_both.json`.
   - The generated `_source_key` changes.
   - The generated `referencias.id` changes.

Current likely result:

- The old `only_eciglogistica` reference remains.
- The old link remains active.
- The new `matched_both` reference is inserted separately, or the load can fail on unique `sku`/`ean13`.

## Proposed Direction From Discussion

Treat the process pipeline as the more intelligent source of truth for matching decisions, but do not let the pipeline bucket become DB identity.

Preferred loader behavior should be link-first:

- For solo Eciglogistica or solo Vaperalia rows:
  - If a matching distributor link already exists, refresh/update it.
  - If no matching distributor link exists, create a provisional `referencia` and create the link.

- For matched pairs:
  - If neither side exists in `referencia_distribuidora_links`, create one new `referencia` and create both links.
  - If exactly one side exists, attach the missing distributor link to that existing `referencia`.
  - If both sides exist and point to the same `referencia_id`, refresh/update both links.
  - If both sides exist but point to different `referencia_id` values, leave both existing rows untouched, report the split-reference conflict, skip that matched item, and continue loading the rest.
  - If an exact distributor + URL + variant lookup returns multiple rows, leave those rows untouched, report all conflicting links, skip that input item, and continue loading the rest.

Important refinement:

- The loader can trust the pipeline that a pair matches.
- The loader still needs to guard DB invariants and handle contradictory historical DB state.

## Risks To Avoid

- URL-only identity can collapse distinct variants that share the same product URL.
- "Do nothing if URL exists" leaves stale scraped fields, price, title, `scraped_at`, and activity status unchanged.
- Two existing links for a matched pair can point to different references. The current policy deliberately leaves that historical split untouched and reports it for later cleanup; it does not make the pipeline pairing canonical in the DB.
- Missing products from a later scrape currently remain active unless an explicit deactivation rule is added.
- Scraped values such as URL, product reference, synthetic reference, variant label, and product title are useful fingerprints, but they are not authoritative primary keys.

## Mutable URL / Link Conflict Contingency

Current link ID generation includes URL:

```text
stable_id("link:" + side + ":" + source_key + ":" + url + ":" + variant)
```

The DB also has a uniqueness rule on:

```text
referencia_id + distribuidora_id + variante
```

Risk:

- If a distributor changes the product URL for an already matched/reference-linked item, the loader generates a new `referencia_distribuidora_links.id`.
- The logical DB identity may still be the same `referencia_id + distribuidora_id + variante`.
- Because the current SQL uses `on conflict (id)`, it will not catch the existing composite-identity row.
- PostgreSQL can reject the insert on the unique constraint for `referencia_id + distribuidora_id + variante`.

Required contingency:

- Treat URL as mutable observed metadata, not link identity.
- Generate link IDs from stable link identity, preferably:

```text
link:<referencia_id>:<distribuidora_id>:<variante>
```

- Or upsert links by the natural DB key:

```sql
on conflict (referencia_id, distribuidora_id, variante) do update set
  url = excluded.url,
  base_url = excluded.base_url,
  source_title = excluded.source_title,
  source_reference = excluded.source_reference,
  source_brand = excluded.source_brand,
  price_tax_excluded = excluded.price_tax_excluded,
  scraped_at = excluded.scraped_at,
  updated_at = excluded.updated_at,
  activo = excluded.activo,
  deleted_at = excluded.deleted_at,
  variants_json = excluded.variants_json
```

Preferred implementation:

- Do both:
  - remove URL from generated `referencia_distribuidora_links.id`;
  - use conflict handling that updates the existing row when `referencia_id + distribuidora_id + variante` already exists.

Expected behavior after this change:

```text
same reference + distributor + variant + new URL -> update existing link
```

not:

```text
new URL -> attempt to insert a separate link
```

## Open Question

Define what makes a `referencia_distribuidora_links` row `activo`:

- Is it active because it appeared in the latest scrape?
- Is it inactive when absent from a full distributor refresh?
- Should partial/category-limited runs avoid deactivating anything outside their scope?
- Should an unavailable/out-of-stock product remain active if still visible in the catalog?
- Should `deleted_at` represent disappearance from source, explicit deactivation, or logical deletion from canonical matching?

## Current `activo` Finding

As currently implemented, `activo` is not determined by the scraper.

- `scraper/src/types.ts` has no stock, active, available, deleted, first-seen, or last-seen field.
- `scraper/src/exporter.ts` does not export any activity/availability field.
- `prepare-products-json.js` does not carry any activity/availability field into prepared CSVs.
- `load_master_to_postgres.py` hardcodes each emitted link as active:
  - `activo = True`
  - `deleted_at = None`
  - `scraped_at = now`
  - `updated_at = now`
- On upsert, `activo`, `deleted_at`, and `scraped_at` are overwritten from the current payload.
- Rows absent from the current payload are not touched, so an old active link remains active forever unless another process changes it.

The architecture docs mention Eciglogistica `option[data-stock]` and say to keep it as metadata if present, but the actual `EciglogisticaConnector` currently only extracts the option display value and discards `data-stock`.

Conclusion: today `activo` means "this link was present in a payload that the loader emitted at some point, and has not been manually changed later." It does not mean "seen in the latest full scrape" or "in stock."
